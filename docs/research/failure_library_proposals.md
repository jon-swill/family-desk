# Failure library proposals

Proposed additions to `FAILURE_LIBRARY.md`. Nothing here is a rule until the owner approves it (Phase 1 task O6). Then A9 merges it with the next F-/R- numbers and records the final ID here. Status is `proposed`, `approved` or `rejected`. The Phase 1 gate (G-4) needs every row to be `approved` or `rejected` and the owner-decision column to have no blanks.

P-01 to P-06 come from the Phase 1 plan reviews in `docs/phases/phase_1/phase_1_eval.md` (first review 2026-11-24, re-review 2026-11-25). A4 adds retail-algo post-mortems and broker-API incidents below them, and B11 adds patterns found in the spike.

| ID | Pattern | Source | What happens | Root cause | Proposed rule | Status | Owner decision | Final ID |
|---|---|---|---|---|---|---|---|---|
| P-01 | Unanchored audit trail | Phase 1 plan review, 2026-11-24 | A hash chain checked only against itself still verifies after it is rewritten end to end or cut short at the tail | The chain's head is stored only inside the log it protects | Each log's final `seq` and head hash are recorded somewhere independent (committed evidence, the daily owner digest). The verifier takes the expected head as input and fails on any mismatch | approved | approved 2026-11-25 | |
| P-02 | Vacuous liveness ("silent equals fine") | Phase 1 plan review, 2026-11-24 | A broken monitoring path (wrong subscription, a filter that never matches, a CIK padding mismatch, an empty positions list) produces the same "nothing happened" output as a healthy, quiet one | Silence is accepted as evidence without proof the path is alive | Every data path proves it is alive on a known positive (subscription ack, unfiltered sample count, read-only REST cross-check, real payload) before its silence counts as evidence | approved | approved 2026-11-25 | |
| P-03 | Spike code promoted to production | Phase 1 plan review, 2026-11-24; compare F-01 Knight (retired code reactivated) | Prototype code and its bypass flags reach the production path without design review | Convenience: the spike already works, so it gets reused | Spike code lives in a quarantined package that later phases must not import; bypass flags are removed before the next phase; production code is written from the reviewed spec | approved | approved 2026-11-25 | |
| P-04 | Trade-capable key doing read-only work | Phase 1 plan review, 2026-11-24; compare F-04 3Commas | Read-only intent is enforced only by our own code, because the key itself can trade | The broker offers no read-only key, or none was requested | Use a read-only or least-privilege key wherever the broker offers one. Where it doesn't, record the accepted risk in RETRO and keep code guards over both code and dependencies. (For Phase 1 the owner has already accepted this risk: RETRO 2026-11-25) | approved | approved 2026-11-25 | |
| P-05 | Shared-identifier attribution | Phase 1 plan re-review, 2026-11-25 | One issuer identifier covers many instruments (a fund trust's CIK spans many ETFs), so an event for one is attributed to another, and the false match is welcomed as the long-awaited positive case | The symbol-to-identifier map assumes one-to-one | Every symbol-to-identifier map records cardinality (unique / shared / none). Shared or missing identifiers never attribute an event to a single symbol unless a second key (series or class ID) also matches | approved | approved 2026-11-25 | |
| P-06 | Shadowed safety check | Phase 1 plan re-review, 2026-11-25 | A demo or test meant to show check X trips check Y first, so X is never shown working live, yet the evidence reads as if it were | Checks stop at the first failure and report no reason | Every refusal reports a specific reason code (or the full list of failed checks), and every refusal demo asserts the code it intends to prove | approved | approved 2026-11-25 | |
| P-07 | Retry after an ambiguous order outcome duplicates the order | First-hand: [Kite Connect forum, June 2021](https://kite.trade/forum/discussion/9962/order-is-getting-placed-after-python-api-gives-error). Broker side: [Alpaca status, 29 May 2026 timeouts](https://status.alpaca.markets/incidents/jrx7xvv59ldm); [FINRA AWC 2020066971201, Robinhood, p. 22](https://www.finra.org/sites/default/files/2021-06/robinhood-financial-awc-063021.pdf) | The order POST times out on the client ("Read timed out. (read timeout=7)"); the bot treats it as failed and sends a second order; the first order also reaches the market (the poster says about 38 seconds later), leaving "1 extra unwanted order". Broker incidents create the same ambiguity: Alpaca reported about nine minutes of timeout errors across live and paper Orders APIs; in Robinhood's 9 March 2020 outage it "was unclear to Robinhood's customers whether existing orders were being executed" and about 166,000 orders were stuck "pending" | A timeout or connection error is treated as "not sent" when the true state is unknown; the retry carries a new identity, so the broker can't de-duplicate it | Every order gets a deterministic `client_order_id` derived from its intent ID, written to the ledger before the request is sent. A timeout, 5xx or dropped connection puts the order in state `unknown`; it is never re-sent as a new order. It is resolved only by looking up that `client_order_id` at the broker. While any order is `unknown`, the kernel refuses new orders for that symbol, and after a configured time it halts entries and pages the owner. Test: a fake broker that accepts the order and then times out the response must end with exactly one order | proposed | | |
| P-08 | Two instances of the bot trade the same account | First-hand: [xqliu, DEV Community, 2 Mar (incident 25 Feb)](https://dev.to/xqliu/two-losses-two-systemic-bugs-automated-trading-post-mortem-from-okx-and-hyperliquid-427l) (crypto; the author says the account is run by an AI agent); [nuniesmith/crypto PR #27, 17 Oct 2026](https://github.com/nuniesmith/crypto/pull/27) | A scheduled run (every 30 minutes) and a manual run of the same executor fired together; "No concurrency guard existed. Both paths called the exchange API, both got filled", so the position was double the intended size and the stop-out loss doubled. In the second case a copy of the bot traded a deposit on 2026-10-14 and nothing noticed; the fix added an hourly check for executed orders missing from the bot's own ledger | Nothing enforces "one writer per account"; the bot assumes every order on the account is its own | The trading process takes an exclusive OS-level lock on startup and exits non-zero if it can't. Every `client_order_id` carries a run ID. Reconciliation (rule 9) flags any broker order or fill not in our ledger as `foreign`; a foreign order halts entries and pages the owner. Tests: a second process started against the same config exits without connecting; a fake broker holding an untagged order trips the halt | proposed | | |
| P-09 | Protective stop accepted but not working | First-hand: [xqliu, DEV Community, 2 Mar](https://dev.to/xqliu/two-losses-two-systemic-bugs-automated-trading-post-mortem-from-okx-and-hyperliquid-427l) (OKX, crypto); [Alpaca forum, 26 May 2021, paper](https://forum.alpaca.markets/t/some-bracket-orders-don-t-have-stop-loss/5797) | The stop placement returned success (`code: 0`) but had failed on the exchange (`order_failed`); price ran through the intended stop, and when the bot tried to re-set it the exchange refused because the price was already beyond it, so a fallback closed the position at a worse price. The author found the same silent failure in four past placements. On Alpaca paper, a user's batch of bracket orders showed take-profit legs but "for quite a few of the orders, there is no stop loss sell order"; many stop legs showed as cancelled (no root cause confirmed in the thread) | An "accepted" response is treated as proof that protection is resting; nothing re-checks that every position stays protected | After placing a protective stop, the bot reads it back by ID within a configured number of seconds and requires a working status (`new`, `accepted`, or `held` while the parent is unfilled). Every cycle it checks: for each open position, working protective quantity = position quantity. On a breach it re-places once with a marketable-limit collar (R-25/R-26), then halts entries and pages the owner. Extends invariant 4, which says stops rest at the broker but doesn't say how we know. Test: a fake broker that accepts a stop and then reports it rejected or cancelled trips the check | proposed | | |
| P-10 | Session-time logic shifts by an hour at a DST change | Vendor release note: [TradersPost, 11 Mar 2024](https://docs.traderspost.io/releases/march-11th-2024) | After the March clock change, users' "from and to trading window times moved forward by an hour"; the vendor fixed the root cause, but users also had to edit their own settings. A bot whose window shifts trades into the open or close it was meant to avoid, or misses its exit | Session times are stored as fixed clock values or UTC offsets instead of being derived from an exchange calendar in the exchange's time zone | All session logic (open, close, early closes, holidays, R-24's no-trade minutes) is computed in `America/New_York` with the IANA tz database from an exchange calendar; no fixed UTC offset appears in code (a test greps for it). At startup and daily the bot cross-checks its calendar against the broker's clock and calendar endpoints and refuses to trade on disagreement. Tests cover both DST transition days and an early-close day using `FakeClock` | proposed | | |
