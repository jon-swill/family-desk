# Failure library proposals

Proposed additions to `FAILURE_LIBRARY.md`. Nothing here is a rule until the owner approves it (Phase 1 task O6). Then A9 merges it with the next F-/R- numbers and records the final ID here. Status is `proposed`, `approved` or `rejected`. The Phase 1 gate (G-4) needs every row to be `approved` or `rejected` and the owner-decision column to have no blanks.

P-01 to P-06 come from the Phase 1 plan reviews in `docs/phases/phase_1/phase_1_eval.md` (first review 2026-11-24, re-review 2026-11-25). A4 adds retail-algo post-mortems and broker-API incidents below them, and B11 adds patterns found in the spike.

| P-07 | Retry after an ambiguous order outcome duplicates the order | First-hand: [Kite Connect forum, June 2021](https://kite.trade/forum/discussion/9962/order-is-getting-placed-after-python-api-gives-error). Broker side: [Alpaca status, 29 May 2026 timeouts](https://status.alpaca.markets/incidents/jrx7xvv59ldm); [FINRA AWC 2020066971201, Robinhood, p. 22](https://www.finra.org/sites/default/files/2021-06/robinhood-financial-awc-063021.pdf) | The order POST times out on the client ("Read timed out. (read timeout=7)"); the bot treats it as failed and sends a second order; the first order also reaches the market (the poster says about 38 seconds later), leaving "1 extra unwanted order". Broker incidents create the same ambiguity: Alpaca reported about nine minutes of timeout errors across live and paper Orders APIs; in Robinhood's 9 March 2020 outage it "was unclear to Robinhood's customers whether existing orders were being executed" and about 166,000 orders were stuck "pending" | A timeout or connection error is treated as "not sent" when the true state is unknown; the retry carries a new identity, so the broker can't de-duplicate it | Every order gets a deterministic `client_order_id` derived from its intent ID, written to the ledger before the request is sent. A timeout, 5xx or dropped connection puts the order in state `unknown`; it is never re-sent as a new order. It is resolved only by looking up that `client_order_id` at the broker. While any order is `unknown`, the kernel refuses new orders for that symbol, and after a configured time it halts entries and pages the owner. Test: a fake broker that accepts the order and then times out the response must end with exactly one order | proposed | | |
| P-08 | Two instances of the bot trade the same account | First-hand: [xqliu, DEV Community, 2 Mar (incident 25 Feb)](https://dev.to/xqliu/two-losses-two-systemic-bugs-automated-trading-post-mortem-from-okx-and-hyperliquid-427l) (crypto; the author says the account is run by an AI agent); [nuniesmith/crypto PR #27, 17 Oct 2026](https://github.com/nuniesmith/crypto/pull/27) | A scheduled run (every 30 minutes) and a manual run of the same executor fired together; "No concurrency guard existed. Both paths called the exchange API, both got filled", so the position was double the intended size and the stop-out loss doubled. In the second case a copy of the bot traded a deposit on 2026-10-14 and nothing noticed; the fix added an hourly check for executed orders missing from the bot's own ledger | Nothing enforces "one writer per account"; the bot assumes every order on the account is its own | The trading process takes an exclusive OS-level lock on startup and exits non-zero if it can't. Every `client_order_id` carries a run ID. Reconciliation (rule 9) flags any broker order or fill not in our ledger as `foreign`; a foreign order halts entries and pages the owner. Tests: a second process started against the same config exits without connecting; a fake broker holding an untagged order trips the halt | proposed | | |
| P-09 | Protective stop accepted but not working | First-hand: [xqliu, DEV Community, 2 Mar](https://dev.to/xqliu/two-losses-two-systemic-bugs-automated-trading-post-mortem-from-okx-and-hyperliquid-427l) (OKX, crypto); [Alpaca forum, 26 May 2021, paper](https://forum.alpaca.markets/t/some-bracket-orders-don-t-have-stop-loss/5797) | The stop placement returned success (`code: 0`) but had failed on the exchange (`order_failed`); price ran through the intended stop, and when the bot tried to re-set it the exchange refused because the price was already beyond it, so a fallback closed the position at a worse price. The author found the same silent failure in four past placements. On Alpaca paper, a user's batch of bracket orders showed take-profit legs but "for quite a few of the orders, there is no stop loss sell order"; many stop legs showed as cancelled (no root cause confirmed in the thread) | An "accepted" response is treated as proof that protection is resting; nothing re-checks that every position stays protected | After placing a protective stop, the bot reads it back by ID within a configured number of seconds and requires a working status (`new`, `accepted`, or `held` while the parent is unfilled). Every cycle it checks: for each open position, working protective quantity = position quantity. On a breach it re-places once with a marketable-limit collar (R-25/R-26), then halts entries and pages the owner. Extends invariant 4, which says stops rest at the broker but doesn't say how we know. Test: a fake broker that accepts a stop and then reports it rejected or cancelled trips the check | proposed | | |
| P-10 | Session-time logic shifts by an hour at a DST change | Vendor release note: [TradersPost, 11 Mar 2024](https://docs.traderspost.io/releases/march-11th-2024) | After the March clock change, users' "from and to trading window times moved forward by an hour"; the vendor fixed the root cause, but users also had to edit their own settings. A bot whose window shifts trades into the open or close it was meant to avoid, or misses its exit | Session times are stored as fixed clock values or UTC offsets instead of being derived from an exchange calendar in the exchange's time zone | All session logic (open, close, early closes, holidays, R-24's no-trade minutes) is computed in `America/New_York` with the IANA tz database from an exchange calendar; no fixed UTC offset appears in code (a test greps for it). At startup and daily the bot cross-checks its calendar against the broker's clock and calendar endpoints and refuses to trade on disagreement. Tests cover both DST transition days and an early-close day using `FakeClock` | proposed | | |
| P-11 | Acting on a lagging fill update sells twice and goes short | First-hand, Alpaca paper: [Alpaca forum, 26 May 2021](https://forum.alpaca.markets/t/replace-order-creates-a-new-order-successfully-but-the-old-order-is-filled-later-thus-creating-duplicate-order/5794); broker control: [Alpaca account configurations reference](https://docs.alpaca.markets/reference/patchaccountconfig-1) | Exiting XLF, a user's limit sell had already filled 312 shares (13:34:50 in the log), but the fill update hadn't reached the bot; it sent a replace at a new price (13:35:35), got a success response with a new order ID, and then placed another sell for the same shares, which left the account short. Alpaca staff: "a current issue with slow updates on fills in the paper trading environment" | Order state is taken from the bot's last-seen update, not confirmed with the broker before a replace or a new exit; nothing caps a sell at the shares actually held | The kernel computes sellable quantity = long position in our ledger minus every open, `unknown` (P-07) or pending sell; it rejects any sell above that, so no automated path can go short (invariant 16). A replace or new exit for a symbol runs only after the broker confirms the prior order's status and `filled_qty`. Where the broker offers a long-only switch (Alpaca `no_shorting`: "If true, account becomes long-only mode") it is set on every automated account and asserted at startup with the other startup checks (R-13); a mismatch refuses to run. Test: a fake broker that delays fill events while a replace is sent must end flat, never short | proposed | | |
| P-12 | Market-data stream goes silent without an error | Official: [Alpaca status, 15 Oct 2026](https://status.alpaca.markets/incidents/8tvqz47bxs2v); [Alpaca status, 19 Nov 2026](https://status.alpaca.markets/incidents/yj0gf2k7fb64); staff answer on reconnects: [Alpaca forum, Oct 2022](https://forum.alpaca.markets/t/t-error-code-406-msg-connection-limit-exceeded/10896) | A vendor-side network disruption hit Alpaca's IEX and SIP streams: "New bars and trades may not be updating for impacted symbols." Alpaca itself paused notional and fractional entries to "prevent orders from executing at stale prices"; the page describes no in-protocol staleness signal. On 19 Nov 2026 an upstream provider issue gave stale prices on the options stream. Separately, a client that reconnects without closing the old socket can be refused with 406 "connection limit exceeded", because the server keeps "partially dead" connections for 90 seconds and (per staff in 2022) "Only one active real-time connection is allowed" | Staleness is judged by "the socket is open" instead of by the age of the data; reconnect logic opens a second session before the first is gone | Staleness is measured per symbol as now minus the exchange timestamp of the last quote or trade, from a trusted clock, with a configured threshold; a stale symbol takes no entries (makes R-24 testable). Quotes pass a sanity check at the boundary (bid > 0, ask >= bid). Before each order the stream price is cross-checked against a REST snapshot within a tolerance. Reconnect closes the old socket, backs off and logs each attempt; repeated 406s halt entries and page. Tests: a `FakeClock` plus a fake stream that stays connected but stops sending trips the stale check | proposed | | |
| P-13 | Request-rate limit hit, blocking the calls that matter | First-hand: [Alpaca forum, May 2024](https://forum.alpaca.markets/t/unexpected-429-since-may-1st/14132); [Alpaca forum, 30 Apr 2024](https://forum.alpaca.markets/t/429-rate-limit-exceeded-when-creating-orders/14120) | A bot whose limiter was meant to allow 2 calls per second sent seven trading GETs within about 0.75 s and got HTTP 429 on the orders endpoint; staff: "You are simply placing too many calls" and "Your rate limiting logic must not be working." Staff state the Trading API limit is 200 calls/min per account, independent of the market-data subscription. A second user hit 429 "quickly" with async order POSTs. While throttled, a bot can't cancel or protect any more than it can enter | No single request budget across the process; polling and retries spend the same allowance that cancels and protective orders need | One client-side token bucket covers every trading-API call, sized at a configured fraction of the broker's documented limit (default 50%), with a reserved share only cancels and protective-stop calls may use. Polling is replaced by streams where the broker offers them. A 429 halts entries, honours the reset header with capped exponential backoff and is logged. Test: with a `FakeClock`, a burst of N requests never exceeds the budget, and a cancel still goes through when entries have used their share | proposed | | |
| P-14 | Paper fills flatter the strategy | Official: [Alpaca paper trading docs](https://docs.alpaca.markets/docs/paper-trading) | Alpaca paper does not simulate market impact, "Price slippage due to latency", queue position for non-marketable limits, price improvement, regulatory fees or dividends; "Your order quantity is not checked against the NBBO quantities"; and orders get random partial fills "10% of the time". Paper P&L can therefore look better than live would, and forward-test promotion (rule 7) would rest on cost-free fills | Paper results are read as if they were live results | Every paper fill is re-scored in our ledger with modeled costs: priced at the far side of the NBBO at decision time plus a configured slippage, with fees from the published schedule; an order larger than the displayed size is flagged. Rule 7's forward tests and any paper-to-live promotion use only the cost-adjusted figures. The strategy code handles a random partial fill on every order type (tested with a fake broker that partially fills) | proposed | | |
| P-15 | Broker-reported balances, fills or order status are wrong | Regulator: [FINRA AWC 2020066971201, Robinhood, 30 Jun 2021](https://www.finra.org/sites/default/files/2021-06/robinhood-financial-awc-063021.pdf); [InvestmentNews, 5 Nov 2019](https://www.investmentnews.com/ria-news/robinhood-traders-uncovered-a-glitch-that-gave-them-infinite-leverage/170593) (secondary); Alpaca official: [status, 20-21 May 2026](https://status.alpaca.markets/incidents/wy443l1k5rrz), [status, 12-13 Nov 2026](https://status.alpaca.markets/incidents/sll2gy6tbcw4); first-hand, Alpaca live: [Alpaca forum, Aug 2021](https://forum.alpaca.markets/t/wrong-filled-qty-reported-for-closed-oco-sell-orders/6397) | FINRA found Robinhood showed inaccurate cash balances to more than 135,000 customers (Dec 2019 to Jun 2020), doubling negative balances or showing buying power as "cash", and showed about 4.2 million customers doubled "negative buying power". In 2019 Robinhood "incorrectly adds the value of those calls to the user's own capital", inflating borrowing power. Alpaca: after "a restart of the principal engine" a subset of overnight fractional limit orders got duplicate executions, giving wrong filled quantities and a buying-power issue; on 12 Nov 2026 options fills were "incorrectly updated to rejected or canceled in error". A live Alpaca user saw phantom partial fills on OCO stop legs, so "the API returns the same info" and the algorithm believed it was 209 shares short | The bot treats the broker's numbers as ground truth, so a broker bug flows straight into sizing, exits and reconciliation | Our ledger is built independently from our own intents and fill events (de-duplicated by execution ID), never copied from broker summaries. Reconciliation (rule 9) compares ours with the broker's positions, cash, open orders and fills; a mismatch beyond a configured tolerance halts entries on that account and pages the owner. Nothing trades automatically to "fix" a mismatch, and neither side is overwritten without an owner-acknowledged ledger entry. Sizing uses the lowest of our settled cash, broker cash and broker buying power. A status that moves backwards (filled to cancelled or rejected) or a fill above order quantity is flagged as a broker anomaly. Tests with a fake broker that double-reports a fill or flips a filled order to cancelled | proposed | | |
| P-16 | Broker API retired or changed under a running bot | Regulator: [FINRA AWC 2020066971201, Robinhood, p. 22](https://www.finra.org/sites/default/files/2021-06/robinhood-financial-awc-063021.pdf) (9 Mar 2020); first-hand, unofficial Robinhood API: [robin_stocks issue #521, Dec 2024](https://github.com/jmfernandes/robin_stocks/issues/521); Schwab migration: [tda-api maintainer's transition notes](https://tda-api.readthedocs.io/en/latest/schwab.html) | When TD Ameritrade accounts moved to Schwab, the maintainer of the main Python wrapper wrote that a transitioned account "will lose access to the TDAmeritrade REST API", that "all API wrappers will stop working on that account", and that a new application (new API key) had to be registered. On 9 Mar 2020 a venue changed the messaging protocol it used with Robinhood; the change was not tested, Robinhood's order entry "was unable to process incoming messages due to an internal coding error" and stayed down for 45 minutes. Users of the unofficial `robin_stocks` library found TOTP-based login "was working until Dec 17" (2024) and then failed with `KeyError: 'detail'`; workarounds took months and some needed a person to approve the login on a phone, which unattended automation can't do | An outside interface changes without notice (or, for an unofficial API, with no contract at all) and the client either crashes or misreads the new response | Automation uses only official, documented broker APIs (no reverse-engineered or unofficial ones; see COMPLIANCE.md). The broker SDK is pinned. Boundary parsers fail closed: an unknown order status, enum value or missing field raises and halts entries; it is never mapped to a default. A daily paper contract test exercises every endpoint we use and fails the next session's start on any schema change. Broker deprecation and migration notices are tracked in RETRO with their dates | proposed | | |
| P-17 | Forced re-authentication stops an unattended bot | Official: [IBKR TWS API docs, daily and weekly reauthentication](https://www.interactivebrokers.com/docs/tws-api/doc/tws-settings/daily-weekly-reauthentication); Schwab (no official page reachable without a developer login): [schwab-py authentication docs](https://schwab-py.readthedocs.io/en/latest/auth.html) | Schwab Trader API: the access token "is only valid for thirty minutes", refresh tokens "are only good for seven days", after which refresh requests "are rejected with an invalid_client error"; "There is currently no way to make a refresh token last longer than seven days", and a new token needs an interactive login. IBKR: TWS and IB Gateway restart daily (API users are told to choose "Auto restart"), and "The weekly authentication cycle starts on every Monday"; a `Soft token=0` login failure "means you need to manually login again". A bot that nobody re-authenticated stops managing its orders until a person logs in | Credential and session lifetimes are treated as setup trivia rather than as state the system must track and alarm on | Each broker session records its credential expiry time as data. The owner is alerted at T-48h and T-24h. The trading session is not armed if credentials expire before that session's close. An auth failure mid-session halts entries (protective stops already rest at the broker, invariant 4) and pages the owner. The bot never automates MFA (no TOTP seeds or passwords in the bot). Daily or weekly restarts are scheduled outside market hours and followed by a full reconciliation (rule 9) before the first order. Tests with `FakeClock`: an expiring token blocks arming, and a mid-session 401 halts entries | proposed | | |
| P-18 | A price outside the range the code assumed | Regulator: [CFTC release 8432-21, 28 Sep 2021](https://www.cftc.gov/PressRoom/PressReleases/8432-21) (IBKR, 20 Apr 2020) | When WTI crude futures settled below zero, IBKR "did not adequately prepare and configure its electronic trading system to recognize negative prices": negative prices weren't shown to customers, customers couldn't enter negative-priced limit orders, and internal minimum margin wasn't properly enforced before trades executed. The CFTC says hundreds of accounts took losses, which the firm initially estimated at more than $82.57 million; IBKR paid a $1.75 million penalty, with full credit for $82.57 million it had already paid customers. Equities can't go negative, but zero, missing, crossed or absurd prices reach every feed, and collar or sizing maths on them divides by zero or produces a nonsense limit | Code and data models silently assume a value domain ("prices are positive and sane") that the real world can leave | Every numeric field is validated at the boundary against an explicit domain (finite; equity and ETF prices > 0; bid <= ask; quantities within configured bounds; timestamps in the session). Out-of-domain values raise and mark the symbol untradable for the session; they are never clamped, defaulted or passed on. The kernel refuses any order whose reference price fails the domain check. Property-based tests feed zero, negative, NaN, infinite and very large values through the parsers, sizing and collar functions | proposed | | |
